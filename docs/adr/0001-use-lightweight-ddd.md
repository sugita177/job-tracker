# ADR 0001: 軽量ドメイン駆動設計 (Lightweight DDD) の採用

- **ステータス**: 承認 (Accepted)
- **日付**: 2026-09-22
- **決定者**: 開発者

## 1. コンテキストと課題
Laravel標準のActiveRecordパターン（Eloquent）は迅速なプロトタイピングに適しているが、複雑な業務ロジック（求人応募のライフサイクル、状態遷移ガード、面接ステップ追加の整合性）を実装するにあたり、以下の問題が生じやすい：
- ControllerやEloquentモデルにビジネスルールが散乱し、Fat Controller / Fat Model化する。
- Eloquentモデルはデータベース接続と密結合しているため、単体テスト（TDD）の実行速度が遅くなり、テストの保守性が落ちる。
- 一方で、Java等で一般的な「厳格なフルDDD（オニオンアーキテクチャやヘキサゴナル）」をそのままLaravelに持ち込むと、ボイラープレートが激増し、Laravel本来のエコシステム（DI, FormRequest, Eloquent, Gate/Policy）の良さを殺してしまう。

## 2. 決定事項
本プロジェクトでは、**「軽量ドメイン駆動設計（Lightweight DDD）」** を採用する。

1. **ドメイン層の純粋性**:
   - `JobApplication` などの集約ルートおよび値オブジェクト（`ApplicationStatus`, `ApplicationChannel`, `Priority`）は、フレームワークに依存しない純粋なPHPクラスとして実装する。
   - ビジネスルールや不変条件はすべてこのドメインモデルに集約し、DB接続不要の高速なTDD（Pest / PHPUnit）を実現する。
2. **インフラ層との明確な分離（相互マッピング）**:
   - Eloquentモデルはインフラストラクチャ層のデータ永続化クラス（テーブル定義）としてのみ扱い、ビジネスロジックは持たせない。
   - リポジトリクラス内で `toDomain()` / `toEloquent()` の相互変換を行う。
3. **Laravelエコシステムの積極的活用**:
   - バリデーションは `FormRequest`、認可は `Gate / Policy`、JSON変換は `JsonResource` を採用し、車輪の再発明を避ける。
   - トランザクション管理やユースケースのオーケストレーションは `UseCase` クラスが担う。

## 3. 結果・影響 (トレードオフ)

### プラス面 (メリット)
- **高いテスタビリティ**: ドメインロジックの単体テストがミリ秒単位で実行可能となり、TDDのフィードバックループが極めて高速になる。
- **ドメインルールの保護**: 外部からの意図しないプロパティ変更や不正な状態遷移をドメイン層で100%防止できる。
- **可読性・保守性**: 「ビジネスルールはDomainディレクトリ」「DB操作はInfrastructure」と責務が明確。

### マイナス面 (デメリットと緩和策)
- **マッピングのオーバーヘッド**: ドメインエンティティとEloquentモデルの間でデータ変換コードを書く必要がある。
  - *緩和策*: MVPでは集約ルートが少数（`JobApplication`, `Company`）に絞られているため、オーバーヘッドは最小限に抑えられる。
